## What Problem Does It Solve?

Normally, a Load Balancer can send each new request to:

DIFFERENT BACKEND INSTANCES

Example:

REQUEST #1

↓

EC2 #1

REQUEST #2

↓

EC2 #2

REQUEST #3

↓

EC2 #3

But some applications need the same client to continue communicating with:

THE SAME BACKEND INSTANCE

This is called:

SESSION STICKINESS

or:

SESSION AFFINITY

### Memory Trick

STICKINESS

=

SAME USER → SAME TARGET

---

## What Is Load Balancer Stickiness?

Stickiness allows a Load Balancer to associate a client with:

ONE SPECIFIC TARGET

for a period of time.

Think:

USER A

↓

LOAD BALANCER

↓

EC2 #1

Then:

USER A RETURNS

↓

LOAD BALANCER

↓

EC2 #1 AGAIN

Instead of potentially sending the next request to:

EC2 #2

or:

EC2 #3

### Memory Trick

STICKY SESSION

=

STAY WITH THE SAME SERVER

---

## Why Is Stickiness Needed?

Some applications store:

SESSION DATA

locally on an EC2 instance.

Example:

USER LOGS IN

↓

SESSION CREATED ON EC2 #1

↓

NEXT REQUEST GOES TO EC2 #2

↓

EC2 #2 DOES NOT KNOW THE SESSION

This can cause the application to behave incorrectly.

With stickiness:

USER

↓

EC2 #1

↓

EC2 #1

↓

EC2 #1

The user's session remains associated with the same backend.

---

## Stickiness Uses Cookies

Load Balancer stickiness is implemented using:

COOKIES

Think:

CLIENT

↓

COOKIE

↓

LOAD BALANCER

↓

SAME TARGET

The cookie allows the Load Balancer to recognize the client and maintain:

SESSION AFFINITY

### Memory Trick

STICKINESS

=

COOKIE

---

## Cookie Expiration

The stickiness cookie has an:

EXPIRATION DATE

The expiration controls:

HOW LONG

the client remains associated with the same target.

Think:

COOKIE ACTIVE

↓

SAME TARGET

COOKIE EXPIRES

↓

LOAD BALANCER CAN SELECT ANOTHER TARGET

### Memory Trick

COOKIE LIFETIME

=

STICKINESS LIFETIME

---

CLB

COOKIE STICKINESS

TARGET GROUP

STICKINESS ENABLED

↓

TARGETS

### Memory Trick

ALB STICKINESS

=

TARGET GROUP SETTING

## Cookie Types

Your course distinguishes two main cookie approaches:

APPLICATION-BASED COOKIES

and:

DURATION-BASED COOKIES

Think:

WHO CREATES / CONTROLS THE COOKIE?

↓

APPLICATION

or

LOAD BALANCER

---

## Application-Based Cookies

Application-based stickiness uses a cookie associated with:

THE APPLICATION

There are two types:

CUSTOM COOKIE

and:

APPLICATION COOKIE

---

## Custom Application Cookie

A custom cookie is generated by:

THE TARGET APPLICATION

Think:

APPLICATION

↓

CREATES COOKIE

↓

LOAD BALANCER USES COOKIE

The cookie can include:

CUSTOM ATTRIBUTES

required by the application.

The cookie name must be specified:

INDIVIDUALLY

for each target group.

### Memory Trick

CUSTOM COOKIE

=

APPLICATION CREATES IT

---

## Reserved Cookie Names

Certain cookie names are reserved by AWS and should not be used for custom application cookies.

Examples include:

AWSALB

AWSALBAPP

AWSALBTG

Think:

AWS COOKIE NAME

↓

RESERVED

### Exam Thinking

If AWS generates and manages a cookie name:

DO NOT REUSE IT

for your own custom application cookie.

---

## Application Cookie

ALB can also use an:

APPLICATION COOKIE

for application-based stickiness.

Think:

APPLICATION SESSION

↓

COOKIE

↓

ALB MAINTAINS AFFINITY

The important exam concept is:

APPLICATION-BASED STICKINESS

=

COOKIE ASSOCIATED WITH APPLICATION BEHAVIOR

---

## Duration-Based Cookies

Duration-based stickiness uses a cookie generated by:

THE LOAD BALANCER

The ALB-generated cookie is:

AWSALB

Think:

ALB

↓

GENERATES AWSALB COOKIE

↓

CLIENT RETURNS COOKIE

↓

ALB SENDS CLIENT TO SAME TARGET

### Memory Trick

AWSALB

=

LOAD BALANCER COOKIE

## Duration-Based Stickiness Flow

First request:

CLIENT

↓

ALB

↓

EC2 #1

ALB returns:

AWSALB COOKIE

↓

CLIENT

Next request:

CLIENT + AWSALB COOKIE

↓

ALB

↓

EC2 #1

Think:

COOKIE

↓

REMEMBERS TARGET

## Stickiness and Load Distribution

Stickiness can create:

LOAD IMBALANCE

Why?

Some users may generate:

MORE REQUESTS

than other users.

Example:

100 HEAVY USERS

↓

EC2 #1

while:

20 LIGHT USERS

↓

EC2 #2

Because clients remain tied to specific targets:

TRAFFIC MAY NOT BE EVENLY DISTRIBUTED

### Memory Trick

STICKINESS

=

BETTER SESSION CONSISTENCY

BUT

POSSIBLE LOAD IMBALANCE

---

## Stickiness Does Not Make the Target Healthy

Stickiness does not mean the Load Balancer will continue sending traffic to:

AN UNHEALTHY TARGET

Think:

USER

↓

STICKY TO EC2 #1

EC2 #1 FAILS

↓

HEALTH CHECK FAILS

↓

LOAD BALANCER MUST USE HEALTHY INFRASTRUCTURE

### Exam Trap

STICKINESS

≠

IGNORE HEALTH CHECKS

---

## Better Stateless Architecture

Although stickiness can solve session problems, cloud architectures often benefit from:

STATELESS APPLICATION SERVERS

Instead of storing session state only on:

ONE EC2 INSTANCE

store shared session information in an external service.

Think:

USER

↓

ALB

↓

ANY EC2 INSTANCE

↓

SHARED SESSION STORE

This makes horizontal scaling easier because:

ANY SERVER

can handle the user's request.

### Memory Trick

STATELESS

=

ANY SERVER CAN HANDLE THE REQUEST

---

## Stickiness vs Stateless Design

### Sticky Architecture

USER

↓

SAME EC2

↓

LOCAL SESSION

Advantage:

SESSION CONSISTENCY

Possible disadvantage:

LOAD IMBALANCE

---

### Stateless Architecture

USER

↓

ANY EC2

↓

SHARED SESSION DATA

Advantage:

EASIER HORIZONTAL SCALING

Think:

STICKINESS

=

REMEMBER THE SERVER

STATELESS

=

SERVER DOESN'T MATTER

---

## Stickiness and High Availability

Stickiness should not be confused with:

HIGH AVAILABILITY

Stickiness determines:

WHICH TARGET RECEIVES A CLIENT'S REQUEST

High Availability determines:

WHETHER THE APPLICATION SURVIVES FAILURE

Think:

STICKINESS

=

SESSION ROUTING

HIGH AVAILABILITY

=

FAILURE RESILIENCE

---

## Stickiness and Auto Scaling

Sticky sessions can still be used with:

[[Auto Scaling Groups]]

Think:

ALB

↓

TARGET GROUP

↓

AUTO SCALING EC2 INSTANCES

However, applications should be designed carefully because:

TARGETS CAN BE ADDED

and:

TARGETS CAN BE REMOVED

This is another reason stateless application designs are often easier to scale.
